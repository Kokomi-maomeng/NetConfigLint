## 三平台门禁

GitHub CI 覆盖 Windows、Linux 和 macOS，Python 3.12 / 3.13 与 Qt 6.9 / 6.11 的运行边界。
严格类型检查使用发行版 Qt 6.11.2 类型声明；Qt 6.9 的类型声明遗漏了可运行的 Property 装饰器和
invokeMethod 重载，因此其运行测试仍保留，类型检查不依赖这些旧声明。

三个系统分别编译后在独立 Unicode / 空格目录中运行原生与软件渲染烟雾。
Linux CI 使用 Xvfb；CI 虚拟设备结果不代表所有物理显卡、显示缩放或桌面会话。
Linux / macOS 的编译目录仅供 CI 运行验收，不作为 Release 资产分发；本次分发许可和完整
SBOM 门禁针对用户要求的 Windows 便携包。Unix 的重定位 / 签名会改变库字节，不能将其冒充为
Windows 门禁所验证的原始 wheel 二进制。

最终源码验证见 [CI 34767464222](https://github.com/Kokomi-maomeng/NetConfigLint/actions/runs/34767464222)。
其中 Python 3.13.2 / Qt 6.11.2：Windows 32.46 秒，Linux 29.36 秒，macOS 32.61 秒，
各 499 项通过。首次集成发现的新增诊断翻译遗漏已修复，并加入 next-table 诊断翻译回归。

Linux 原生启动使用 [Qt 官方 XCB 依赖清单](https://doc.qt.io/qt-6/linux-requirements.html) 补齐环境，
`ldd` 预检精确发现缺少 libxcb-shape.so.0 后已补入 libxcb-shape0。
这次仅修复 CI 环境；应用源码和 Windows 包不变，使用单独的 Linux 构建重试。

Windows CI 的 MSVC 编译链会从宿主系统或 Visual Studio 复制 VC 运行库。许可门禁对这一来源补充了
严格验证：限于已知 VC 运行库名称，必须与指定系统 / VS 分发目录的文件哈希一致，且 Authenticode
状态有效、签名主体为 Microsoft Corporation。来源以不含本机路径的名称进入 SBOM；未匹配或未签名
文件仍被拒绝。12 项相关测试通过，并实际验证微软签名文件接受、未签名文本拒绝。

Windows 构建还统一处理了 Nuitka 的两种 DLL 布局：部分编译环境会把 Qt 库放在根目录，
不能只清理 PySide6 子目录。依赖收集现在从程序、Python 扩展、保留的动态插件和软件渲染辅助库
出发，跟踪普通及延迟导入；依赖不完整时拒绝继续清理。未使用的模块不会因已被复制而保留。
Windows 文件名大小写差异不再阻止来源匹配，但仍要求上游文件哈希完全一致。

本次仅增加构建脚本验证：依赖闭包、大小写来源、VC 运行库及许可反例共 18 项通过。
在隔离的编译产物副本中额外放入 144 个根目录 Qt 库，清除 120 个无用库，缺失依赖 0；
该副本通过完整许可门禁及系统 PATH 下的非提权原生启动、三种导出和 QML 检查。
这是对新构建路径的定向验证，不替换下方已完成全部验收的最终本地 ZIP。

云端后续构建已通过完整编译和许可门禁（612 个文件、13 个组件），但 CI 的 PowerShell
直接调用 GUI 程序后提前读取了尚未生成的结果文件。启动步骤改为显式等待进程退出并限制为
90 秒后，再检查结果；同一调用方式在隔离编译目录下的原生与软件渲染均已验证，各导出
3 份报告、QML 错误 0。该问题属于 CI 等待顺序，不修改应用或已验收的便携包。
最后一次 Windows 定向构建已完整通过，云端 Python 3.13.2 / Qt 6.11.2 的 Direct3D11 与
Software 均正常退出并生成完整结果；最终没有再执行未改变的源码矩阵或其他系统构建。

## 发布隐私与许可

源码、提交内容、作者身份及 ZIP 分别检查；报告只记录位置和类别，不输出敏感值。
新增提交使用项目 noreply 身份，原始设备配置、个人机器审计和测试导出不进入发布内容。

Qt 官方二进制中已有的构建机路径只在与已核实官方 wheel 完全同哈希时单独记录；应用代码和
修改过的二进制不能使用该例外。固定上游许可、实际分发文件清单及 SBOM 在最终 ZIP 上再次核对。
本次源码与 ZIP 均无待解释的敏感模式命中；44 份官方 Qt 二进制按固定 wheel 的逐文件哈希单独记录。

历史；因此本报告不声称旧历史完全不存在个人资料。
