# 公开内容隐私规则

本规则适用于 NetConfigLint 的 Git 提交、分支、标签、PR、Issue、评论、Actions 日志和附件、Release 正文及资产。目标是在公开之前发现个人资料。自动检查不能识别所有姓名、域名、截图或压缩数据，发布负责人仍须复核实际内容。

## 提交和推送

1. Git 作者、提交者、附注标签只使用 GitHub 提供的 `users.noreply.github.com` 邮箱，GitHub 平台提交允许 `noreply@github.com`。不要使用私人联系邮箱；历史提交和合并提交没有豁免。
2. 本地克隆首次使用时运行 `python scripts/install_privacy_hooks.py`。它只设置本仓库的 hooks，供关联 worktree 共用；移动克隆后重新安装。提交前检查暂存内容和实际身份，推送前检查完整待发送历史和全部本地标签。缺少检查程序或规则文件时停止操作。
3. 手动复核待提交差异，再运行 `python scripts/privacy_guard.py --refs HEAD --tags`。自动检查覆盖未知邮箱、常见令牌/私钥、个人目录、电话形态值及私有资料路径；输出只记录位置、类别和对象编号，不回显匹配值。
4. 私有审计报告、原始身份映射、凭据、真实设备资料、历史用户数据及本地归档不得进入 Git。保留 `.gitignore` 对 `archive/`、`release/`、`build/`、`docs/audits/` 等目录的隔离；不要强制添加这些目录。
5. PR 合并须通过 `Public data privacy` 检查，主分支启用必需检查、禁止强推及删除。附注标签的 tagger 由 hooks、CI 和发布脚本检查。当前个人仓库的作者/提交者邮箱正则规则请求被 GitHub 拒绝（HTTP 422），不能声称已在服务端拦截所有分支的私人邮箱；账号的邮箱保密及命令行暴露邮箱阻止选项保持开启。CI 运行在推送之后，不能代替本地检查。

## 内容和例外

示例使用合成数据、文档地址段及 `example.com`、`.example`、`.invalid`、`.test` 等示例域。联系人、电话、设备名、真实公网地址和日志上下文须人工脱敏。测试所需假令牌应拼接构造，不能加入真实凭据。

`.privacy-policy.json` 仅记录已核验的公开第三方联系信息、协议标识和资源名称的 SHA-256。字体表内的随机邮箱形态仅允许已核验字体文件的精确 SHA-256，文件变化后重新核验；此例外不跳过凭据或个人路径检查。不得把私人邮箱加入允许表来消除告警。更新规则必须在变更说明中记录公开来源及用途，并复核扫描前后的命中变化。

图片、视频、压缩文件、二进制和上传到网页的正文/附件须另行检查。发布前检查截图可见内容和元数据、安装包实际展开内容、日志、SBOM 与校验文件。未知结果保持“未验证”，不能用自动扫描无命中代替人工审阅。网页编辑也必须遵守此规则。

## 发布门禁

发布前同时满足：完整提交及标签身份检查通过；现有 `audit_release.py` 和安装包实际内容检查通过；所需平台 CI 合格；SBOM、标签目标、工作流来源及公开资产校验信息一致。Release 工作流在写入草稿前再次检查隐私。不要复用不对应当前提交的历史 CI，不要绕过失败门禁。

2026-10-08 的邮箱历史清理仅重写身份元数据及其后继提交编号，保留各旧版本的文件树。既有发布资产保持原字节及校验和，其 SBOM 的构建编号属于清理前的构建事实；不可修改旧包或伪造新的构建证明。旧包的严格编号校验可能因标签重写而失败，应使用本地受控映射和树一致性证据解释。新发布必须使用清理后的提交重新构建并取得对应 CI 证据。

## 旧历史和平台残留

旧克隆、worktree、私有 bundle 和备份可能仍保存原始邮箱。不要从旧历史直接推送或合并；重新获取已清理的远端，未发布工作以审阅后的补丁迁入，再执行完整门禁。清理材料保持本地私有，不上传含原始身份的映射或备份。

分支和标签重写不等于清除 GitHub 的 PR 引用、缓存、已有下载副本和外部克隆。平台只读引用需要单独验证并按 GitHub Support 的处理结果记录状态，未确认前不能称为彻底清除。发现凭据时先撤销/轮换，再处理历史。本项目此次确认的是私人邮箱记录，没有据此认定发现有效令牌。
